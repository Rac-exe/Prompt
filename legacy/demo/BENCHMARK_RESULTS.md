# PRMPT Benchmark Results — First Real Run

> Complete analysis of the 60-run benchmark conducted June 8–12, 2026. Every result number, every methodology decision, every confidence caveat, and every implication for product strategy — explained in full.

---

## Section 1: What This Benchmark Is Testing (And What It Is Not)

### What It Is Testing

This benchmark tests **routing and optimization value on first-try bug fixes**. Specifically:

- Does having PRMPT's MCP available (with precomputed optimized context) reduce the total cost of a Claude Code or Codex CLI session compared to running the same session without PRMPT?
- Does adding an optimized prompt (PRMPT-rewritten) on top of the MCP routing further improve results?
- Does the answer change depending on whether the agent is allowed to search the codebase on its own (soft) or must rely only on PRMPT (hard)?

The success criterion is binary: **net cost decreases AND the bug is still fixed (pass rate held).**

A "win" requires both conditions. A variant that fixes the bug more cheaply is a win. A variant that fixes the bug the same way at lower cost is a win. A variant that costs more, even if the bug is still fixed, is a loss.

### What It Is NOT Testing

**The live agentic retrieval loop.** The MCP server used in this benchmark (`prompt_mcp_server.py`) serves precomputed answers. When the agent calls `prmpt_optimize_task`, it gets a JSON file generated by `prepare.py` before the benchmark ran — not a live retrieval from the code intelligence service. The multi-hop agentic loop in `agent_loop.py` does not run during these sessions.

**The "fix it again" determinism fix.** The retry escalation path (passing `error_signal` and `previous_attempt_chunk_ids` to get different files on a second attempt) is wired in code but no caller drives it. This benchmark does not test what happens when PRMPT is asked to suggest different files after a failed first attempt.

**Real user prompt distribution.** All 9 task prompts are controlled (written by the team to represent clear bug descriptions). Real developer prompts are messier, more ambiguous, shorter, longer, and more varied. This benchmark tests "PRMPT with reasonably-clear bug reports" not "PRMPT with whatever a developer actually types."

**Multi-attempt sessions.** All benchmark runs are single-attempt. The agent gets one shot. Real developer sessions often involve iteration: "it still doesn't work," "try a different approach," "what if the bug is somewhere else?" None of that retry behavior is captured here.

**Read this result as: "routing/optimizer baseline on first-try controlled tasks."** Everything else is future work.

## Section 2: External Context — How Claude Code and Codex Actually Charge

### Understanding the Cost Numbers

All costs in this benchmark are in US dollars billed via OpenRouter. The cost numbers are not estimates — they are the actual OpenRouter usage delta (spend before run subtracted from spend after run).

**Claude Code** uses Claude Sonnet 4.5 (the default model as of June 2026):

- Input tokens (not cached): $3.00 / million tokens
- Output tokens: $15.00 / million tokens
- Cache-read tokens: $0.30 / million tokens (10x cheaper than non-cached input)
- Cache-write tokens: $3.75 / million tokens (slightly more than non-cached to write)

**Context replay and caching:** Claude Code aggressively caches its context. The system prompt, already-read files, and prior conversation turns are written to the cache on first access and read at $0.30/million on subsequent turns. This is why Claude Code's per-session cost is much lower than naive token-counting would suggest.

**Codex CLI** uses GPT-5 Codex (OpenAI, accessed via OpenRouter):

- Pricing is broadly comparable to Claude Sonnet in absolute terms but Codex has less sophisticated prompt caching (as of June 2026)
- Without the cache efficiency Claude Code has, Codex pays closer to full input token price for context replay

**The structural difference this creates:** A 15-turn Claude Code session might pay full price for only the first 2–3 turns and cache-read prices for the rest. A 15-turn Codex session pays closer to full price throughout. This makes PRMPT's turn-reduction much more valuable for Codex (saving turns saves full-price tokens) than for Claude (saving turns saves mostly cheap cache-read tokens).

### What "PRMPT Cost" Means in This Benchmark

PRMPT's cost has two components:

**Component 1 — Amortized prepare cost** ($0.0489 per task): The `prepare.py` script ran before any benchmark session. It indexed all three repos via the code intelligence service and optimized all 9 task prompts via the optimizer service. The total cost of this phase was $0.4404. Divided across 9 tasks: $0.0489 per task. This cost is added to every MCP variant cell's PRMPT cost column.

**Component 2 — Live session PRMPT spend**: During the benchmark sessions themselves, PRMPT's own LLM calls (the optimizer and code intelligence services) spent money via OpenRouter. The usage delta captures this. In the first run, the precomputed MCP server made no additional LLM calls during agent sessions (it served from a file). So Component 2 was $0.00 for the first run. The $0.0489 amortized cost is the entire PRMPT cost per cell.

**Why this matters for interpreting results:** The $0.0489 PRMPT overhead is a fixed cost regardless of session complexity. For a Codex session that costs $0.10 raw, a $0.0489 overhead is 49% of the baseline — hard to overcome with routing savings. For a Codex session that costs $0.40 raw, $0.0489 is 12% — easy to beat with 20% routing savings. The benchmark results show this dynamic clearly: Codex on larger/harder tasks shows bigger savings, while tasks with lower raw costs show smaller or negative savings.

## Section 3: The Three Test Repos

### Why These Repos

The three repos were chosen (and generated at scale) to represent realistic startup codebases:

1. **Realistic scale:** Each repo is ~100,000 lines. A smaller repo would make the routing problem trivial (20-file codebases are easy to navigate without guidance). A larger repo would be too slow to benchmark repeatedly.
2. **JavaScript/TypeScript:** The most common language used with AI coding CLIs (based on Claude Code and Codex usage patterns). All repos use ES modules.
3. **Comprehensive test suites:** Each repo has `npm test` that passes when the bug is fixed and fails otherwise. This is the oracle — no human judgment required.
4. **Seeded bugs with known fixes:** The bugs are realistic (multi-file interactions, logic errors) but deterministic (one correct fix that makes tests pass).

### orbit-crm-generated (~104,657 lines)

A CRM (Customer Relationship Management) platform with contacts, leads, workspaces, import reconciliation, and workspace membership management. The most complex of the three repos.

**orbit-p1 (not in this run):** Workspace import reconciliation bug — imported workspace leads corrupting lead assignment and workspace visibility. Multi-component: `reconcileWorkspaceImport.js`, `leadScoring.js`, `authorizeWorkspace.js`. Excluded from the first run due to its complexity and higher variable prepare cost.

**orbit-p2 (in this run):** A variant of the import reconciliation bug focused on duplicate lead creation when workspace membership was malformed. The bug involved: checking for inactive workspaces before lead creation, handling missing owner pools, duplicate detection logic.

**orbit-p3 (in this run):** Workspace visibility authorization — a missing status check in `authorizeWorkspace.js` that allowed leads to be visible in inactive workspaces. Simpler than p2 but still touches 3 files.

**Why orbit is the hardest:** PRMPT's prepare cost for orbit tasks is higher than for atlas/nova. The complex import reconciliation scenario required more optimization tokens ($0.09–$0.17 per orbit task vs $0.049 for atlas/nova). This higher overhead means the routing savings need to be larger to produce a net win.

### atlas-commerce-generated (~104,599 lines)

An e-commerce platform with orders, inventory, payments, discounts, and fulfillment pipelines.

**atlas-p2 (in this run):** Order fulfillment discount application bug — discounts calculated in the wrong order (percentage discounts applied after fixed discounts instead of before), causing incorrect total amounts. Touches `orderCalculation.js` and `discountEngine.js`.

**atlas-p3 (in this run):** Inventory reconciliation import mismatch — a bug in how import batch reconciliation handled variant inventory counts, causing stock levels to be incorrect after bulk imports. Touches `inventoryReconcile.js`, `importBatch.js`, `variantStock.js`.

**Why atlas shows the best Codex results:** Atlas-p3 has the largest raw Codex baseline cost ($0.42) and the bug was well-suited to PRMPT's routing (a tight 3-file interaction). The combination of high raw cost + good routing signal = 52% savings.

### nova-support-generated (~104,624 lines)

A customer support platform with ticket management, routing rules, SLA tracking, priority scoring, and notification systems.

**nova-p2 (in this run):** SLA breach notification timing bug — notifications fired at the wrong time due to an off-by-one error in the breach threshold calculation, using microseconds instead of milliseconds in one comparison. Touches `slaManager.js` and `notificationScheduler.js`.

**nova-p3 (in this run):** Ticket routing priority scoring bug — priority scores weren't normalized correctly when multiple routing rules applied simultaneously, causing some high-priority tickets to be deprioritized incorrectly. Touches `routingEngine.js` and `priorityCalculator.js`.

**Why nova shows consistent but moderate Codex savings:** Nova's bugs are well-isolated (2-file interactions) with moderate raw costs ($0.33–$0.40). PRMPT's routing correctly identified the relevant files, giving consistent 10–42% savings across all four nova Codex cells.

## Section 6: Per-Task Deep Dives

### atlas-p3 — The Showcase Task

**Raw costs:** Claude $0.33, Codex $0.42

**Why Codex wins so big (52% best):** Atlas-p3 involves a 3-file inventory reconciliation bug. Raw Codex without guidance explored broadly — reading 15+ files before finding the right 3, running multiple `grep` searches. Total exploration added ~$0.22 in unnecessary input tokens. PRMPT's routing pointed directly to `inventoryReconcile.js`, `importBatch.js`, `variantStock.js`. Codex read those 3 files, found the bug, fixed it.

**Why Claude wins at all on this task (7–11%):** Claude raw costs $0.33 — higher than the $0.22 baseline seen on simpler tasks. Claude was doing more exploration than usual here. The atlas-p3 bug is in an area of the codebase where Claude's heuristics led it to read more files than necessary. PRMPT's routing was genuinely useful in constraining Claude's exploration.

**Why mcp_optimizer is worse than mcp_only for Codex on atlas-p3:** The optimized prompt was slightly longer and more descriptive. This added input tokens to every turn's context. The mcp_only variant with a short vague prompt + MCP routing was actually cheaper because the prompt itself was shorter.

**Lesson:** For Codex on clearly-routable tasks, `mcp_only` may beat `mcp_optimizer` because prompt optimization adds tokens without adding routing value (the routing is already perfect from the MCP tool call).

---

### orbit-p2 — The Structural Loss

**Raw costs:** Claude $0.40, Codex $0.26

**Why Codex loses on orbit-p2:** The orbit-p2 raw Codex cost ($0.255) is unusually low — the bug was well-isolated enough that raw Codex found it efficiently without needing guidance. This happens: not every task benefits from routing. When the agent's baseline navigation is already efficient, PRMPT's $0.049+ overhead is a tax, not a savings.

Additionally, orbit-p2's PRMPT costs are higher than other tasks: the complex CRM import reconciliation scenario required more optimization tokens during prepare. Several orbit-p2 cells show PRMPT costs of $0.06–$0.11 vs the standard $0.049. This higher overhead further erodes the potential savings.

**Why Claude loses badly on orbit-p2 most cells:** Claude raw at $0.404 is reasonable for this complex task. Adding PRMPT overhead ($0.05–$0.11) plus the MCP routing didn't help Claude fix it more efficiently — Claude's native exploration was already targeted. The worst cell (mcp_only/hard: $0.602) had PRMPT costing $0.109 (high prepare overhead) on top of an agent cost of $0.493.

**The exception — orbit-p2/claude/mcp_optimizer/hard:** This cell shows $0.402 net ($0.352 agent + $0.051 PRMPT) vs $0.404 raw — a 0.25% win. The optimizer produced a prompt that was slightly better than Claude's default for this specific bug. The hard hardening forced Claude to follow the MCP route instead of exploring. The result: barely a win. A second run might easily flip this to a loss.

**Lesson:** High-complexity tasks with tight file interactions don't always benefit from routing. When the raw agent is already efficient OR when the PRMPT prepare cost is disproportionately high, routing adds overhead without recovering it.

---

### orbit-p3 — Codex Wins, Claude Pays the Most

**Raw costs:** Claude $0.34, Codex $0.48

**Why Codex wins here (15–40%):** Orbit-p3 has a high raw Codex cost ($0.479) — Codex was exploring broadly in the orbit-crm codebase without guidance. PRMPT correctly identified `authorizeWorkspace.js` as the primary file. With routing, Codex cost $0.29–$0.40 depending on variant. Hard mcp_optimizer at $0.288 is the best — 40% saving.

**Why Claude loses so badly (worst: -76.55%):** The orbit-p3/claude/mcp_optimizer/soft cell is the worst result in the entire dataset. Net cost: $0.599 vs $0.339 raw. The agent cost alone was $0.426, and PRMPT's cost was $0.173 (very high — the orbit-p3 task required significant optimizer tokens for the complex CRM context).

What likely happened: the soft hardening variant allowed Claude to use native search AND the MCP. Claude read the MCP result but then continued its normal exploration anyway — cross-checking the MCP's suggestions against its own analysis. This doubled the context: both the exploration Claude would have done anyway AND the MCP overhead. With hard hardening (blocked from native search), the same task cost $0.428 — still a loss vs raw $0.339, but much smaller.

**Lesson for orbit-p3/claude:** Hard hardening significantly reduces the loss. Without it, Claude's tendency to validate against native exploration defeats any savings from the MCP routing. This is the strongest evidence in the dataset for why soft hardening is insufficient for Claude + PRMPT.

### nova-p2 — The Best Soft Win

**nova-p2/codex/mcp_optimizer/soft: +41.68%** ($0.233 vs $0.400 raw)

This is the strongest evidence that PRMPT can win even without hard hardening. Codex raw on nova-p2 spent $0.400 in broad exploration. PRMPT's optimizer produced a precise 2-file prompt. In the soft variant, Codex received both the optimized prompt AND the MCP routing — and chose to follow it without falling back to native search. The result: $0.184 agent cost + $0.049 PRMPT = $0.233 total, a 41.68% saving.

**Why soft beats hard for nova-p2/codex/mcp_optimizer:** The optimized prompt was already so precise that Codex didn't need to search. In the hard variant ($0.304), the hard hardening config itself added overhead — Codex had to make more MCP calls to compensate for denied native searches. Counterintuitive: for a well-optimized prompt, soft hardening produces better results because the agent can use the optimized prompt directly without the overhead of multiple MCP calls.

## Section 7: The Claude vs Codex Structural Explanation

This is the most important finding in the dataset. It's worth explaining fully.

### Why Claude Loses

**Claude Code's architecture works against PRMPT for short tasks:**

1. **Prompt caching:** Claude Code caches its context aggressively. Cache-read tokens cost $0.30/million vs $3.00/million for non-cached. Claude's context replay (resending prior turns on each new message) costs 90% less than naive calculation suggests.
2. **Efficient native exploration:** Claude Code's native code navigation (how it uses Glob, Grep, Read) is well-tuned. It reads targeted files, follows references efficiently, and doesn't do unnecessary broad searches on these well-defined tasks. Claude's raw cost on atlas-p2 ($0.220) is already very efficient.
3. **The $0.049 floor:** Every MCP variant adds at minimum $0.049 to the total cost (the amortized prepare cost). For a Claude session that costs $0.220 raw, $0.049 is 22% overhead. PRMPT's routing would need to save Claude 22%+ in agent costs just to break even — and on tasks where Claude is already efficient, there's no 22% waste to recover.
4. **Soft hardening doesn't change Claude's behavior:** Without hard hardening, Claude reads the MCP result AND continues its normal validation. The MCP result becomes additive context, not a replacement for exploration. In several cells, this doubles effective turn count compared to either pure raw or pure hard-MCP.

**The conclusion:** For tasks Claude Code is already good at (well-defined bugs in JS/TS codebases at ~100k line scale), PRMPT is a cost surcharge, not a cost reducer. PRMPT's routing signal doesn't overcome Claude's native efficiency.

### Why Codex Wins

**Codex's architecture creates a gap that PRMPT fills:**

1. **Less aggressive caching:** Codex's prompt cache efficiency is lower than Claude's. Context replay at closer to full-price means more savings from turn reduction.
2. **Broader baseline exploration:** Raw Codex on atlas-p3 costs $0.421. Claude raw on the same task costs $0.329. Codex is spending ~28% more than Claude on the same task because it's doing more exploration. That exploration delta is exactly what PRMPT's routing eliminates.
3. **Routing response:** Codex follows MCP routing more literally. When told "the bug is in inventoryReconcile.js lines 45–80," Codex reads those lines and patches them. It doesn't do the "let me verify this against my own analysis" loop that Claude does. Codex's routing compliance is higher.
4. **The $0.049 overhead is recoverable:** On a $0.40 Codex baseline, $0.049 is 12%. If PRMPT saves 30% in agent cost by routing directly to the right files, the net saving is 30% - 12% = 18%. That's the atlas-p2 result exactly (22% saving, some noise from single repeat).

**The conclusion:** PRMPT's primary value is for AI coding tools with less sophisticated native context management. Codex is the clearest example. As more AI tools enter the market — many of which won't have Claude's level of optimization — the pool of "PRMPT-eligible" agents grows.

## Section 8: What the MCP Call Count Proves

Every MCP variant cell shows `mcp_calls_median = 1.0`. Not 0, not 2. Exactly 1.

**Why this matters:**

In the original mcp-shi benchmark (before mcp-ahh's improvements), some cells showed the agent loading the MCP configuration but making zero actual tool calls. The agent acknowledged the MCP was available but chose not to use it. PRMPT's context and advice were never received by the agent — yet the benchmark counted those runs as "PRMPT-assisted," inflating the apparent success rate.

mcp-ahh fixed this by counting calls from the server's own log file (not from conversation analysis). The result: definitive proof that in every single MCP cell across 48 runs, the agent called `prmpt_optimize_task` exactly once.

**What drove this:** Two factors working together:

1. The hardened instruction prepended to every MCP session: "Call `mcp__prompt__prmpt_optimize_task` first with task=... Treat the returned JSON as the final authoritative route."
2. The tool description: "FINAL AUTHORITATIVE ROUTE. Trust this and move on."

The combination of an explicit system-level instruction AND a compelling tool description achieved 100% tool-call compliance. Neither alone might have been sufficient.

**Why not 2 calls:** In some experiments, agents would call the MCP, get the result, then call it again to "verify" — especially in soft hardening where the agent could also use native search. This benchmark shows agents called it once and moved on. The "DO NOT deliberate, second-guess" instruction in the tool description suppressed the verification pattern.

## Section 9: Confidence Caveats

These are the reasons you should NOT treat these results as definitive proof:

### 1. Single Repeat Per Cell

Every cell has n=1. One run. LLM agent output variance on repeated runs of the same task can be 10–30% of total cost. The nova-p3/codex/mcp_only/soft result of +10.59% saving could easily flip to a small loss on a second run. The atlas-p3/codex/mcp_only/hard result of +52% would likely hold across 3 runs (the saving is large enough to survive variance), but we don't know for certain.

**What's needed:** 3 repeats minimum, report median and IQR. The benchmark harness supports this. It wasn't done for the first run due to cost and time.

### 2. Only p2 and p3 Tasks

P1 tasks (the more complex bugs, particularly orbit-p1 with its 6-component import reconciliation scenario) were excluded. P1 tasks are more representative of the complex bugs where PRMPT's routing might have the highest impact — but also where PRMPT's prepare cost is highest. The first run deliberately used the more standardized p2/p3 tasks.

### 3. All Tasks Are Seeded and Solvable

100% pass rate (every bug was fixed in every cell) tells us these tasks are tractable. Real developer tasks have a much lower baseline pass rate — some bugs are genuinely hard, some are ambiguous, some have dependencies the agent can't resolve. In the real world, PRMPT might affect pass rate, not just cost.

### 4. Synthetic Repos

The three test repos were generated and scaled up. They're realistic in scale and structure but they don't have the history, inconsistencies, legacy debt, and surprising architecture choices of a real years-old codebase. PRMPT might perform differently on a real 5-year-old startup codebase vs a generated one.

### 5. No Variance Data for PRMPT Costs

The `prmpt_cost_median` column shows the amortized prepare cost. The actual per-session PRMPT variance is unknown because the precomputed MCP server made no live LLM calls during agent sessions. When the live server is deployed (each MCP call triggers a real retrieval), PRMPT's cost per session will vary by query complexity.

## Appendix: The mcp-shi vs mcp-ahh Difference

The friend's original benchmark (mcp-shi) had a critical flaw in cost measurement:

**mcp-shi approach:** `prompt_generation_cost = 48962 input tokens × $X + 2461 output tokens × $Y = hardcoded constant`

This constant was subtracted from "savings" to produce the net figure. Problems:

- The constant was estimated, not measured
- It didn't account for varying optimization complexity between tasks
- It didn't reflect actual OpenRouter pricing tiers or volume discounts
- Different sessions could have very different real costs

**mcp-ahh approach:** OpenRouter usage delta. Before each run, snapshot `total_usage`. After each run, snapshot again. Delta = exact billed cost, including any volume discounts, rounded to 6 decimal places.

Additionally, mcp-shi used heuristic MCP call counting (parsing conversation logs). mcp-ahh uses the server's own call log — the server writes a line per call, count the lines.

**The result:** mcp-ahh's numbers are real. They match what OpenRouter's invoice would say. They include the amortized prepare cost explicitly. They account for higher-cost orbit tasks vs lower-cost atlas/nova tasks. Every number in Section 4 above is a real billed dollar amount, not an estimate.
